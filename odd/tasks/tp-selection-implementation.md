# TP Selection Implementation

## Objective
Implement the agreed TP selection stories using Supabase as the authority for authentication, roles, project state, team capacity, and roster permissions.

## Problem and Why
The current React/Vite app is a static shell with only an optional Supabase browser client. There is no Auth integration, database project, schema, migration, RLS, or selection flow. Capacity and role enforcement cannot safely be implemented in the browser alone.

## Scope and Constraints
- Treat `docs/user-stories.md` as the product source of truth.
- Use Google OAuth with any Google account; `ngarciam@unrn.edu.ar` is the only Admin.
- One team selection consumes one project slot. A team has 1-3 participants including the selector; only the selector authenticates, and all participant names can be edited only by that selector at any time.
- Admin creates/edits/archives projects. Do not permanently delete projects. Capacity may not be reduced below current assigned teams.
- Selection creation must atomically recheck project state/capacity and record a database timestamp. One user may have at most one active selection.
- Keep deferred decisions unresolved: archived-project reactivation, Admin UI visibility of teams, retention/deletion of released selection history, and extra name constraints.
- Do not use the concrete values in `.env.example` or read `.env`. Never put a service-role/secret key in frontend files.
- Do not issue Supabase CLI/API/SQL commands, query production, or verify migration status unless the user explicitly changes this instruction. Treat the migration as applied based on the user's report, not as independently verified. Never request secrets in chat.
- Do not insert dummy/test records into production. The user manages any production migration execution or verification; assistant validation is limited to local code.
- TDD mode: unknown; run ordinary functional checks and do not claim RED/GREEN evidence.
- Route: delegated direct implementation because multiple non-trivial files will change.
- No branch, push, PR, or commit is authorized by this task.

## Acceptance Criteria
- Migrations are previewed and applied only to project ref `iotmujqdemabcweqksjl`; no test data is created in production.
- RLS tests cover unauthenticated, regular-user, selector, and Admin boundaries in a safe test environment.
- Any Google account can sign in; only the configured Admin email can mutate/archive projects.
- Archived projects cannot receive new selections and preserve existing active teams.
- A project cannot be reduced below assigned team count; a team consumes one slot regardless of 1-3 participant count.
- Selection creation enforces one active selection per user and atomically rejects full/archived projects, including concurrent last-slot attempts.
- Selection time is generated by the database; user input cannot change it.
- Only the selecting user can update participant names; edits do not affect capacity or selection identity.
- Deferred behaviors remain unimplemented until explicitly decided.
